* Roles and connections

Both ends of a connection are peers. Either shares buffers and opens mirrors of the other's, over the same connection; roles belong to subscriptions, not to connections. Mirrors are never shared again: =spyglass-share= refuses a mirror, so there is no relaying.

One end listens, the other connects. The listener, =spyglass-server-start=, binds 127.0.0.1 only, on a port the system chooses, and writes the port and a random token of 256 bits to its registration file, readable by its owner only. The connecting end holds a /transport/: a function that, called with a continuation, makes a byte stream to the server and passes it with the token. Transports provided:

- =spyglass-tcp-transport=: a socket to a host and port, with a token.
- =spyglass-file-transport=: this host's server, read from its registration file at each connection.
- =spyglass-ssh-transport=: =ssh HOST cat FILE= reads the remote registration file, then =ssh -W 127.0.0.1:PORT HOST= forwards the stream over SSH's standard input and output; its standard error goes to a separate pipe, so that SSH's messages never mix with frames. Works with Windows's OpenSSH server.

Transports never have Emacs wait for the network or for another host. Sockets connect with =:nowait=, the sentinel passing the stream on once open; host names are resolved by another Emacs, =emacs -Q --batch= printing the addresses (=spyglass--resolve=), since Emacs resolves them synchronously, with =:nowait= too, but with glibc's =getaddrinfo_a=; the SSH transport's processes carry on from their sentinels; and a timer ends an attempt still going after =spyglass-connect-timeout= (20 s), deleting its processes. A connect with no answer kept Emacs waiting 7.8 s on macOS's loopback, a minute or two elsewhere. Processes start from the home directory (=spyglass--spawn=): =make-process= checks the current buffer's directory, which may be on a slow network file system when a timer runs, or gone, failing the attempt. The registration file is read without file name handlers, so that a remote name is not fetched through TRAMP.

Starting a process is the one thing Emacs cannot do without waiting: =posix_spawn= runs with the global lock held, from a Lisp thread too. It takes under 2 ms in a fresh Emacs, batch or graphical, even with a 1.7 GB heap; but in an Emacs running for hours on a Mac with an endpoint security agent, sampled with =sample=, the main thread spent 0.1 to 0.9 s in =posix_spawn= for each of its processes, SSH's among them. So the SSH transport keeps the port and token of a stream that authenticated, and connecting again runs only =ssh -W=; it reads the registration again after a stream that did not authenticate, as one to a server that restarted. A stale token sent meanwhile to whatever listens on the old port opens nothing: a server makes a new token whenever it starts. A host where no server is registered still costs one process per attempt. =make lag= and =make lag-gui= measure the longest Emacs ran no timer during attempts of each kind, in a batch and a graphical Emacs; =spyglass-transport-test.el= checks them.

Drover or anyone may supply a transport of its own. The stream is used in binary on both sides (=set-process-coding-system= =binary=): no end-of-line conversion on Windows.

A connection outlives its streams. When a stream breaks, a connecting end tries its transport again after =spyglass-reconnect-delays= (0.2, 1, 2, 5, 10, 30 s, then every 30 s), or delays of its own (=spyglass-connection-set-reconnect-delays=: drover backs off to 5 minutes, a Mac retrying a host switched off for the night through SSH 945 times otherwise, each attempt a process started), which =spyglass-reconnect= with FRESH starts over, re-reading the registration (the SSH transport once a stream failed to authenticate, see below), so that a restarted server with a new port and token is found. A listening end keeps the connection as an orphan for a while: when the same peer instance connects again, its new stream is adopted by the old connection object, and its mirrors resume. It waits for =spyglass-heartbeat-timeout= (40 s), or what an application gave that connection (=spyglass-connection-set-resume=): drover gives a phone, whose streams close as its application leaves the screen, a few minutes. Only =spyglass-disconnect=, a =bye= from the peer, or a server refusing the handshake end a connection for good. A stream breaks when its process ends, when the peer is silent past the heartbeat timeout (see Heartbeats), when a write fails (part of a frame may be on the stream, which nothing can follow), or when an application asks with =spyglass-reconnect=, having found the peer unresponsive by its own measure.

** Heartbeats

A peer frozen, its Emacs stopped or its host asleep, keeps its stream open to the system: only heartbeats tell. Each end looks at a connection every few seconds; past =spyglass-heartbeat-interval= (10 s) without sending or hearing anything, it sends =ping=, which the peer answers at once, and past =spyglass-heartbeat-timeout= (40 s) without hearing anything, it drops the stream. A connection may have settings of its own (=spyglass-connection-set-heartbeat=), so that an application noticing a silent peer within seconds on a local network need not change them for every connection; drover gives 1 and 4 s in its tests, 5 and 20 s otherwise.

The connection is looked at every half of the shorter of the interval and of what the timeout leaves after it (=spyglass--heartbeat-period=): a ping goes within half that after the interval of silence, its answer has the other half to come back before the timeout, and a silent peer is dropped within that much after the timeout, 0.5 s for 1 and 4 s, 5 s by default. The period was half the interval, computed with =/=, which divides integers as integers: 1 halved to 0, and =run-with-timer= makes a timer of no repeat from a repeat of 0, so that a connection given 1 and 4 was looked at once and never again, a peer stopped by SIGSTOP staying connected as long as it was stopped. Settings are taken as floats; the interval and the timeout must be positive and the interval below the timeout, else a peer silent until pinged is dropped first: =spyglass-connection-set-heartbeat= signals an error otherwise, and options set wrong give way to their standard values, with an error reported. =spyglass-conn-test-heartbeat-drops-frozen-peer= stops another batch Emacs with SIGSTOP: it is dropped within 4.5 s, and connects again once SIGCONT resumes it.

* Wire format

A frame is

| bytes | content                                                                                       |
|-------+-----------------------------------------------------------------------------------------------|
|     4 | header length, big endian                                                                     |
|     4 | payload length, big endian                                                                    |
|     H | header: a JSON object, UTF-8                                                                  |
|     P | payload: text encoded in =utf-8-emacs=, which carries every Emacs character, raw bytes too |

The reader accumulates bytes in a unibyte buffer and extracts every whole frame, however the stream splits them. A frame over =spyglass-max-frame-size= (64 MB) is a protocol error and drops the stream; before the handshake succeeds, the limit is 64 KB, so that an unauthenticated stream cannot make the server allocate much.

Text never goes through JSON: it rides in the payload, which costs one encoding and one decoding in C. Surrogate code points, which Emacs buffers may hold but no UTF-8 decoder returns, are replaced by U+FFFD in the payload and listed, with their offsets, in the header.

Lisp values in headers (faces, display specifications, invisibility specs, strings with properties) are encoded as JSON: numbers, strings and booleans as themselves, lists as arrays, symbols as ={"y": NAME}=, dotted pairs as ={"c": [CAR, CDR]}=, vectors as ={"v": [...]}=, strings with properties as ={"S": TEXT, "p": [[START, END, PLIST]...]}=, text JSON cannot hold as ={"B": BASE64}=. Decoding yields data only, bounded in depth; it never calls =read= nor =eval=.

* Protocol

Messages are headers with a type, =t=. After the handshake:

| type      | from      | meaning                                                                                     |
|-----------+-----------+---------------------------------------------------------------------------------------------|
| =hello=   | both      | protocol version, application, instance identifier and name, capabilities; the connecting end's token; =pace= when the sender's writes on the stream block (see Paced streams) |
| =error=   | both      | a refusal or protocol error, then the stream closes                                         |
| =ping=    | both      | heartbeat, stamped with the sender's clock                                                  |
| =pong=    | both      | answer, stamped with both clocks: round trip and clock offset                               |
| =bye=     | both      | clean close: the connection ends for good on both sides                                     |
| =shares=  | owner     | the list of shares, sent on connection and whenever it changes                              |
| =req=/=res= | both    | requests with an identifier; =list= returns the shares                                      |
| =open=    | viewer    | subscribe to a share, under a subscription identifier the viewer chooses; with =resume=, the epoch and the last update applied |
| =u=       | owner     | an update: sequence number, operations, styles, overlays, cursor, description               |
| =resumed= | owner     | the subscription resumed after the given update; frames after it follow                     |
| =ack=     | viewer    | the last update applied                                                                     |
| =close=   | viewer    | end the subscription                                                                        |
| =closed=  | owner     | the subscription ended, with a reason: unshared, killed, no such share, expired             |
| =in=      | viewer    | input: text (=k= "s") or a key in =key-description= form (=k= "k")                          |
| =err=     | owner     | the input was refused or failed                                                             |
| =fl=      | viewer    | fontify this range, which the viewer displays                                               |
| =sz=      | viewer    | the size in cells (=c=, =r=; 0 when hidden) of the window showing the mirror; =f= when it just got focus. Capability =sz= |
| =ch=      | both      | a message of a channel, =ch= its name, its JSON in the payload; a request (=rq=), a reply (=rs=, or =err=), or a chunk (=k=, =n=, =of=), as small as 4 KB to a peer announcing =ck=. Capability =ch= |
| =cha=     | both      | a chunk of a channel received: =k= and =n=. Capability =ch=                                 |
| =rd=      | both      | on a paced stream, the bytes read of it so far, =n=. Capability =pc=                        |
| =fr=      | both      | on a paced stream, a fragment of a frame, its bytes in the payload. Capability =pc=         |

The handshake: both ends send =hello= at once; the server checks the token with a comparison in constant time, the protocol version (equal versions) and the application, and answers =error= and closes otherwise. A client refused tries again later with a fresh registration.

=hello= lists /capabilities/, the optional messages the sender handles (=spyglass-wire-capabilities=). A peer sends such a message only to a peer that announced it: peers of the same protocol version, one older, keep working together, the older one never receiving what it would report as an unknown message; it ignores the capabilities and new keys of =meta= alike. Additions that every peer must understand still change the protocol version.

An update holds:

- =seq=: its number, one more than the last; =reset= with an =epoch= for a snapshot, which empties the mirror first.
- =ops=: replacements =[BEG OLD LEN RUNS]=, applied in order: OLD characters at BEG become the next LEN characters of the payload, with RUNS, a flat vector of lengths and style identifiers (0: no property).
- =sd=: new styles, =[ID PLIST]=, property lists the viewer sanitizes once and keeps; =sr= forgets all styles first. =fd=: attributes of the faces the styles name, for viewers lacking them.
- =ov=: overlays set, =[ID BEG END STYLE]=; =od=: overlays deleted.
- =pt=, =ws=: the owner's cursor and window start, once the viewer has everything.
- =meta=: buffer name, mode name, tab width, truncation, word wrap, invisibility spec, the owner's header line, whether fontification requests help, whether input is taken; for terminals viewers size (=rs=), the terminal's size (=gs=).
- =ct=: when the earliest change it holds happened, on the owner's clock.

* The owner: capture

A subscription keeps the ranges of the buffer its viewer has not seen as /intervals/ =(B BL VL)=: BL characters at B in the buffer replace VL characters of the viewer's copy; they are disjoint and ascending, so the viewer position of an interval is B minus the growth of the intervals before it. Changes, =(OB OL NL)= in the buffer as it was, compose into intervals in one pass (=spyglass--intervals-compose=): overlapping or touching ranges merge, so that 100 000 appends between two captures are one interval. Past =spyglass-max-intervals= (64), the closest neighbors merge, the gap between them resent. A new subscription is one interval: the whole buffer, replacing nothing. When a frame is built, intervals are emitted from the last, so that earlier positions stay valid, and their text is read from the buffer at that moment; a long interval is emitted from its start, a frame of =spyglass-frame-chars= (64 K characters) at a time. Each range's text is encoded once and the frame written in parts, without concatenating the payload. Nothing is queued: a slow viewer costs at most its intervals, its unacknowledged frames and its styles.

Changes are found in one of two ways per share, chosen when the first viewer subscribes:

** Shadow capture

For buffers up to =spyglass-shadow-limit= (16 M characters). The share keeps a hidden copy of the buffer as last captured, with its text properties and copies of its mirrored overlays: the /shadow/. Between 8 and 256 markers, /sentinels/, spread through the buffer split it into segments; their positions in the shadow are remembered. Markers move with every insertion and deletion, even those made with =inhibit-modification-hooks=, as Eat and Ghostel make them. At each capture:

1. A segment whose length changed has changed.
2. A segment of unchanged length may hide a rewrite of equal length. It is compared with the shadow, text and properties (=equal-including-properties= on substrings, memcmp speed), where /hints/ say changes happened: =after-change-functions=, =spyglass-notify= from adapters or callers, jit-lock's fontification. Hints are kept as up to eight regions, as pairs of markers, nearest ones merging, so that a deletion at the top and an append at the end do not hint the whole buffer. When the buffer's =buffer-chars-modified-tick= moved beyond what hooks and hints accounted for, every segment is compared, at most once per ten times the last such comparison took, so that unhinted terminals cost at most a tenth of the main thread.
3. Each changed segment is narrowed to what differs: common prefix and suffix, found by galloping and bisecting comparisons; then, for ranges over 512 characters with as many lines on both sides, line by line, so that a terminal screen with a few changed cells sends those lines only.
4. The changes are applied to the shadow, which the mirrored overlays in it follow; overlays in changed ranges are compared with the owner's, and those differing marked for every viewer.

A sweep compares 32 K characters of buffer and shadow, and the overlays there, every 0.25 s while the buffer is quiet, so that a change no hook or hint told of (an overlay moved, remade or deleted far from changed text, a property set silently) reaches viewers eventually: within =size / 32 K × 0.25= seconds, 3 s for 400 K characters. Overlays changed along with text nearby, as Markdown renderers make them, go with the text at once; code changing overlays alone can call =spyglass-notify= with PROPS-ONLY to send them at once.

** Direct capture

For larger buffers: =after-change-functions= record changes into the share's pending intervals; =before-change-functions= notices a change of text made without hooks before this one. A change of text without hooks (=buffer-chars-modified-tick= moved past what hooks saw) resends the whole buffer as one interval. Overlays are not mirrored, and silent property changes are seen only when hinted.

** Properties

Mirrored text properties (=spyglass-text-properties=): =face=, with =font-lock-face= standing for it where font lock shows it, =invisible=, =display=, =line-prefix=, =wrap-prefix=, and optionally =help-echo=. Overlay properties (=spyglass-overlay-properties=): =face=, =invisible=, =display=, =line-prefix=, =wrap-prefix=, =before-string=, =after-string=, =priority=; overlays of the owner's windows (with a =window= property, or a face such as =region= or =hl-line=) are left out. Each distinct set of properties becomes a /style/, defined once per viewer; the interning keeps frames small (a terminal's thousands of runs share a few dozen styles) and the viewer's work small (each style is sanitized once, and runs reuse its property list). Faces go by name, so that the viewer's theme draws them; each named face also travels once with its attributes as the owner resolves them, which a viewer lacking the face uses instead: the faces of a style's =face=, and those of the strings its other properties hold, a display string's or an overlay's =before-string=, as agent-shell draws its =Me= label (=spyglass-wire-face-names=), and of the owner's mode line and header line. When =font-lock-face= starts or stops showing, the whole buffer is resent. For buffers using jit-lock, the viewer's redisplay asks the owner to fontify what it shows (=fl=), so that mirrors of code are highlighted although the owner never displayed those parts.

* Flow control and resumption

Frames sent to a viewer and not acknowledged count against =spyglass-window= (4 MB). It bounds throughput to a window per round trip: with 1 MB, SSH to a Windows host on the local network carried about 40 MB/s; with 4 MB, the 50 MB/s of the stream benchmark. A write the stream cannot take at once makes Emacs wait inside =process-send-string= (=send_process= retries on EAGAIN after =wait_reading_process_output=, up to 20 ms; Windows's sockets are the exception, see Paced streams), reading no keyboard input meanwhile; measured writes took 0.2 ms at the 99th percentile and 20 ms at most, with either window. Each flush sends for =spyglass-tick-budget= (4 ms) at most, at least one frame per viewer, and the next flush continues at once, so that the command loop runs between frames. While a write waits, timers and process filters do run: sending is not reentered (=spyglass--sending=), a buffer changed meanwhile is captured again before its next frame, and a frame counts as in flight before it is written, since its acknowledgment may arrive during the write. Past it, the owner stops sending to that viewer; changes keep composing into its intervals. The viewer acknowledges once per chunk of input read, for each mirror, with the last update applied. Acknowledgments also measure latency: each frame records when its earliest change happened. What timers and filters send while a write waits is the subject of the next section.

** One writer per stream

Frames are written in several strings: an update's header and the text of each range, so that the payload is never concatenated. Emacs keeps the bytes of one =process-send-string= together, even when a filter writes while it waits (=send_process= queues the latter's behind the former's rest), but not the strings of one frame: a pong, an acknowledgment, a size report or an answer a timer or filter sent while one string waited would go before the next, and the peer would read it as payload, then the rest of the frame as a frame of gigabytes, and drop the stream. It happens as soon as writes wait: under heartbeats, with slow readers, with mirrors in both directions.

So every frame is written by =spyglass--send-frame=, which marks its stream as being written while it writes. A frame sent meanwhile, on that stream, is queued instead, and written by the same call right after the frame in progress, then whatever was queued while that one was written, in order: no timer is involved, and a frame queued goes out as soon as the stream takes it. Senders that may send much while a write waits do not queue: an owner's flush meeting a stream being written schedules itself again (updates are never queued, as above), and channels keep their messages in their own queue (=spyglass--writing-p=). What remains is small, answers to what the peer sends, except the frames a resumption resends, at most a window, which are kept anyway. A peer that sends without reading would make the queue grow: past =spyglass-queue-limit= (64 MB), its stream is dropped. A stream breaking drops its queue with it; a new stream starts with none.

Reading has the same hazard, the other way. A handler writing from the filter, an answer or a channel's acknowledgment, may wait; the filter then runs again, on the same stream, and would handle the frames it reads before those the outer call has yet to handle: across SSH, where pipes fill quickly, channel messages arrived out of order. So =spyglass--filter= handles frames in one call per stream at a time: frames read while it handles others are queued, and the outer call handles them after, in order; mirrors acknowledge after each batch, as before. That queue holds what the peer sends while one of our writes waits for it to read, at most its windows of updates and chunks, and is bounded by =spyglass-queue-limit= too.

** Paced streams

Emacs on Windows writes to a socket without reading meanwhile: =sys_write= in =w32.c= makes every write to a socket block ("TODO: implement select() properly so non-blocking I/O works. For now, make sure the write blocks."), and a write the system cannot buffer waits until the peer reads, Emacs running no timer nor filter. Pipes are spared: there, as on other systems, =send_process= waits reading. With a peer that reads while it writes, as Emacs elsewhere, or =sshd= in front of a Mac's Emacs, such a write ends when the peer reads. Two such ends writing to each other more than the system buffers between them, about 190 KB on Windows 11's loopback, each wait for the other, forever: two Emacs on one Windows host exchanging large channel messages, mirrors both ways, or one Emacs talking to itself, as the tests do. Measured: two batch Emacs on Windows each sending a 4 MB channel message at once both stopped in their second 256 KB chunk until killed; in one Emacs connected to itself, the third 64 KB chunk.

So a stream both of whose ends' writes block is /paced/. Each end says in its =hello= that its writes block, with =pace=, how often to tell it what was read: a quarter of its =spyglass-pace-window= (64 KB). Once both did, and announce the capability =pc=, each end keeps the bytes it wrote and the peer has not said it read below its window: before writing a frame it waits, in =accept-process-output= on the stream, with timers and filters running, as Emacs waits elsewhere, for the peer's =rd=, which carries the count of bytes it read. A frame larger than a quarter of the window goes in fragments, =fr= frames carrying its bytes in their payloads, which the other end puts together and handles in their turn. Every end acknowledges what it read as it reads it, before handling it; while one of its own writes waits, between frames or fragments, the writer writes the acknowledgment it owes, before anything queued: two ends both waiting for the other's acknowledgment while theirs waited behind a frame would wait forever. Acknowledgments are applied by the filter as soon as read, never queued behind the frames a handler's write holds back. The queue of the writer (One writer per stream) and the senders backing off while a write waits work as elsewhere: a paced write is a write that waits.

A stream one end of which reads while it writes is not paced, and pays nothing: the Mac's end of an SSH stream to Windows, its Windows end too, since =sshd= reads. Neither is a stream to a peer predating the capability. Tests force pacing everywhere with =spyglass--pace-streams=: the tests of =spyglass-paced-test.el= and =spyglass-channel-paced-streams= run the tests of whole frames, order, bounded queues, reconnection and channels so on macOS too, and =spyglass-conn-two-emacs-write-at-once= has two Emacs send each other 4 MB at once, paced or not. A 16 MB frame between two ends of one Emacs on Windows takes 0.3 s paced.

** Resumption

Unacknowledged frames are kept. When a stream breaks, the owner's subscriptions of that peer become orphans for =spyglass-resume-timeout= (300 s), still composing changes. When the viewer connects again, it sends =open= with the subscription's epoch and the last update it applied; if the owner still has the subscription with that epoch, it answers =resumed= and resends the frames after that one, then continues; otherwise, a snapshot under a new epoch. A gap in sequence numbers, which a reliable stream never shows, makes the viewer ask for a snapshot.

* Channels

Applications talk over spyglass's connections, rather than open their own beside them, through channels: =spyglass-register-channel= names a channel and its handler, =spyglass-channel-send= sends a message, a JSON object, and =spyglass-channel-request= one awaiting a reply.  A message rides in the payload of a =ch= frame, its JSON once encoded by =json-serialize= and once parsed by =json-parse-string=: text in the header would be parsed twice.  Strings JSON cannot hold, with raw bytes or surrogates, are replaced by U+FFFD on the sender, after =json-serialize= refused the message once, so that a message of clean text is encoded once.  Requests share the connection's identifiers and table of callbacks with spyglass's own, so that a stream ending answers them as it answers =list=.  Channels are a capability, =ch=: nothing is sent on them to a peer not announcing it, a request to it failing at once, and their =:attach= and =:detach= functions hear only of peers announcing it.

Messages of a connection go through one queue, in order, sent from timers for =spyglass-channel-tick-budget= at a time.  One past =spyglass-channel-chunk-size= is cut into chunks, each acknowledged by a =cha= on arrival; at most =spyglass-channel-window= bytes of chunks are unacknowledged, so that a large message, or a slow peer, holds at most that much in flight, the rest waiting in the queue; on a stream whose end here is a pipe, at most what the pipe holds, in chunks of a quarter of it (see Windows of channels).  Acknowledgments go before the queue, so that two peers sending large messages to each other never wait for each other's.  Nothing is written while a write waits on the stream (=spyglass--writing-p=): the connection would queue it apart from the channels' queue, out of the window's reach.  A stream breaking drops the queue and the messages half received: channels resume as the next stream attaches, as mirrors do, through their =:attach= functions.  The receiver bounds what a peer may make it hold: the size announced by a chunked message, at most =spyglass-channel-max-size=, and sixteen messages half received at once.

** Windows of channels

A write a stream cannot take at once makes Emacs wait inside =process-send-string=: =send_process= queues the rest and calls =wait_reading_process_output= for 20 ms, from which output arriving meanwhile brings it back little sooner (such writes took 12 to 22 ms), and Emacs reads no keyboard input meanwhile. A pipe holds 64 KB on macOS and Linux; a socket's buffers grow with the traffic. Windows's pipes behave so too (=sys_write= turns their =ENOSPC= into =EAGAIN=), holding 4 KB unless =w32-pipe-buffer-size= said otherwise when they were made; its sockets block instead (see Paced streams). So through SSH, whose standard input is a pipe, a channel writing its chunks faster than SSH reads them fills the pipe, and Emacs waits 20 ms each time: a clone of drover's took 100 MB from Reaver to Core at 2.7 MB/s, where the other way, Core writing into a socket, took 53 MB/s. Updates of mirrors do not meet it as much: their frames are built as they are written, 64 KB each, and SSH reads one while the next is made (=large-10M= from Reaver: 285 writes, three waiting).

So a stream's end here that is a pipe bounds the channels' window by what it holds (=spyglass--write-capacity=): 64 KB elsewhere than on Windows, and on Windows what spyglass asked for its SSH processes, =spyglass-w32-pipe-size= (4 MB), else what =w32-pipe-buffer-size= says, else 4 KB. Chunks are a quarter of the window, at most =spyglass-channel-chunk-size=, at least 4 KB, to peers announcing =ck=; older peers took at most 129 chunks a message, and get the window and chunks as before. On sockets, =spyglass-channel-window= is 2 MB. =spyglass-pace-window=, the window of paced streams, plays no part between a Mac and Windows: one end of such a stream reads while it writes, and the stream is not paced.

What the tables say:

- Where this end writes into a pipe, filling it costs 20 ms a time, and any window larger than the pipe fills it: past 64 KB, Reaver's rate falls from 21 to 3–5 MB/s, and its own main thread waits 25 to 35 ms at a time. The pipe's capacity, not the round trip, bounds that window, in small chunks: on 10 MB, 48 to 96 KB in chunks of 8 or 16 KB carried 19 to 25 MB/s, 32 KB 15 MB/s, chunks of 32 KB 5 to 15 MB/s, 128 KB in chunks of 16 KB 12 MB/s. On Windows, the pipe is spyglass's to size: 4 MB took Core's sending from 1.5 MB/s to 60, and its timers from 55 ms late to 12.
- Where this end writes into a socket, a larger window carries more, up to 2 MB: 1 MB to 2 MB gained 5 to 10 %, 4 MB nothing more. Messages queued behind chunks in flight wait for 2 MB more at most, 40 ms at 50 MB/s.
- Core's responsiveness hardly depends on the window: receiving, its timers ran as late as idle, 9 to 15 ms at the 99th percentile, 27 ms at most; sending, only a full pipe kept them, up to 55 ms. Its memory grew 12 MB at most, a few pieces in flight and their garbage.
- Reading, Core's pipe of 4 MB rather than 64 KB gained 5 to 15 %; =read-process-output-max= of 256 KB or 1 MB rather than 64 KB changed its rate within the noise of the runs (33 to 55 MB/s on 10 MB), its lateness not at all, and stays the user's. Writing, a window larger than the pipe loses: 4 MB through a pipe of 1 MB carried 41 MB/s on 10 MB, 1 MB 48 to 58.
- Not adaptive: a window probing above the pipe's capacity pays 20 ms for each probe that fills it, and at 128 KB the rate already halves, so that additive increase and multiplicative decrease on the waits would spend more than it gains. Sending at a rate rather than by acknowledgments (32 KB a millisecond, 64 KB in two) carried 10 to 16 MB/s on 10 MB, below the window of 64 KB. The window of a pipe's end bounds the rate by the round trip, 64 KB a round trip: through SSH on a local network that is 21 MB/s; at a round trip of 20 ms, 3 MB/s, what waiting on the full pipe gave anyway.

* The viewer

A mirror is a buffer in =spyglass-mirror-mode=: read-only, no undo, font lock off (faces come from the owner), no process, none of the owner's modes. Updates apply inside =save-excursion=. The mirror shows the owner's cursor (an overlay in =spyglass-cursor=), and windows on it follow the cursor while their point is where it was; moving away to read stops following. Its mode line is the owner's, rendered there with =format-mode-line= in a window showing the buffer, an owner's window else the parking window, and sent in the description (=ml=) as it changes, sanitized, bounded to 500 characters, its faces resolved as text's; without such a window none is sent, as a mode line rendered for a buffer without one shows, in its parts reading the window, the selected window's buffer (Core's moody line named =emacs.org= in a shell's), and the mirror shows what its buffer's =spyglass-mirror-mode-line-function= gives, else Emacs's own. After it, compactly, the mirror's own state: its title or share, the owner, =opening=, =live=, =reconnecting=, =closed= and why, a terminal's size, and =read-only= when its input is refused. The header line is the owner's (=hl=), rendered the same way, and none while the owner has none. The owner's buffer-local face remapping comes too (=fr=), applied with =face-remap-add-relative=, relative to the viewer's own. At the end of the buffer, the owner's cursor is a space shown after the text, which carries =cursor=, so that the window's own cursor there goes on it rather than after it.

Every property value is sanitized on the viewer, whatever the owner did: faces keep names and plain attributes (no function as height), display specifications keep strings, spaces, raising, heights, margins and fringes (no images, no =when=, no forms), invisibility keeps symbols, help echoes keep strings. Unknown face names are replaced by the attributes the owner sent.

* Windows of shared buffers

** Parking

Ghostel renders its terminal only through a window: =ghostel--redraw-now= declines without a /render window/ (any window showing the buffer, graphical ones first), the font and glyph sizes of which it renders with, and output arriving meanwhile stays pending until the buffer is displayed. Even the pty learns of a resize at a render. A shared Ghostel terminal no window shows on the owner would stand still, with its mirrors. Eat and vterm process output and redraw without windows, and need no parking.

A share /needs a window/ when its buffer's =spyglass-needs-window= says so (Ghostel's adapter sets it) or =spyglass-share= was given =:needs-window=. While such a share has subscriptions and no window shows its buffer (the windows of a daemon's initial frame do not count, as Ghostel ignores them), the owner shows it in the root window of a parking frame of its own; polling (=spyglass-poll-interval=) and the subscriptions' events park and unpark. Then the adapter's =spyglass-park-function= renders what was pending. The parking frame is deleted when a window of the user's shows the buffer, the last subscription ends, the buffer is unshared or killed; if something makes it visible, as =display-buffer= does when told to reuse windows of every frame, it is left to the user as an ordinary frame.

A parking frame is made on the display of the selected frame, or of another graphical one, with:

- =visibility= nil, =no-accept-focus=, =no-focus-on-map=, =skip-taskbar=: never shown nor focused. Its focus state stays unknown-false, so Ghostel does not consider the parked terminal looked at (no focus events to the program, no status acknowledged).
- =no-other-frame=: out of =next-frame= and =other-frame=; =desktop-dont-save=: out of desktops and framesets; =tab-bar-lines= 0 and =tab-bar-lines-keep-state=: =tab-bar-mode= leaves it alone.
- =minibuffer= nil: the frame uses the default minibuffer frame's, and has =delete-before= that frame, so that deleting the latter, which Emacs refuses while it serves another frame, deletes the parking frame first; the next poll parks again elsewhere.
- the host frame's =font=; no scroll bars, tool bar or menu bar; =unsplittable=, a dedicated window with =no-other-window=, and an =auto-hide-function= deleting it.
- =after-make-frame-functions= and =before-make-frame-hook= are not run: they are for frames people see (Cocoa's selects every new frame; configurations raise Emacs). =delete-frame-functions= are not run when spyglass deletes it, lest =undelete-frame= remember it.

A frame per buffer, rather than windows of one frame: a parked terminal takes its viewers' size (below), and the windows of one frame share their widths or their heights, so that sizing one would resize the others, sending their programs =SIGWINCH=, and the frame would grow to hold them all. A parking frame costs 3–25 ms to make (Emacs recomputes every face for a new frame: 200 to 1 700 faces) and 0.3 ms to delete; with the Mac port, its window and glyph matrices hold about 2 MB at 80×24 cells, 8 MB at 200×60 and 55 MB at 500×200 (3, 6 and 12 MB with Cocoa), which bounds what a viewer may ask for (=spyglass-max-terminal-size=). Redisplay skips invisible frames: with ten parked buffers changing, a redisplay took at most 0.06 ms more than with them hidden, against 2 ms more with them shown in windows; checking a parked share at each poll takes 25 µs, its window measured again only when the size called for, the window's pixels, the frame's font or the buffer's face remapping change. See [[file:benchmarks.org][the benchmarks]].

Measured windows are selected for an instant, as =window-max-chars-per-line= and Ghostel's renderer do with =with-selected-window=: the selected frame is restored before anything runs, and no hook sees it change.

Platforms: verified on macOS with the Mac port (31.1) and GNU Emacs's Cocoa build (30.2), by =make test-gui=. On Windows, =x-create-frame= honors =visibility= nil and the other parameters the same way (=w32fns.c=); graphical tests were not run there.

** Sizing terminals

A terminal has one grid; programs lay out their screen for it. Each viewer reports the size, in cells of its own font (=spyglass-window-cells=, as Emacs measures windows for processes: =window-max-chars-per-line= by the floor of =window-screen-lines=), of the window showing its mirror: the selected window if it shows it, else the most recently used on a visible frame; 0 when none does. It reports when the mirror opens or resumes, when windows change (=window-size-change-functions=, =window-buffer-change-functions=, gathered for =spyglass-mirror-size-delay=), and with =f= when a mirror's window gets selected in a focused frame. A viewer typing into its mirror is active too.

On the owner, the parties are the viewers whose windows show the terminal and the owner when a window of its shows it, each with the time it was last active: viewers by =sz= with =f=, input and subscribing; the owner by any command run in a window of the terminal (=post-command-hook=) and by its frame getting focus. =spyglass-size-policy= picks: =latest=, the most recently active party, the owner on ties, as tmux's =window-size latest=; =smallest=, the smallest columns and rows; =owner=, the owner's windows when they show it, else the latest viewer. Without any viewer's size, the terminal sizes itself as before.

Terminals size themselves with =window-adjust-process-window-size-function=: Emacs and Eat and vterm (through their processes' =adjust-window-size-function=) call its value with the process and the windows showing it, Ghostel its default value. While a viewer sizes some terminal, spyglass wraps the default value: for a shared terminal, it answers with the policy's size, computing the owner's part with the wrapped function on the owner's windows, parking windows apart; other processes get the wrapped function's answer. So a terminal resizing itself on a change of the owner's windows keeps the size its parties call for, and the owner's windows themselves are never touched. To apply a new size at once, spyglass calls the share's =spyglass-refit-function=: =spyglass-refit-process= calls the process's adjust function as =window--adjust-process-windows= would, windows or not, then sets the pty's size, and again a second later, since Eat and vterm start their program after an =stty= setting the size the terminal had; Ghostel's adapter calls =ghostel--adjust-size= on a window of the terminal, forced, since Ghostel defers a change of rows alone while the minibuffer is active. A parked terminal's parking frame is sized so that its window has the size called for, and Ghostel resizes its grid, and at its next render its pty, from that window. vterm keeps terminals at least =vterm-min-window-width= wide (80).

The terminal's size travels in =meta= (=gs=) for viewers' header lines. Sizes are bounded by =spyglass-max-terminal-size= on the owner, whatever a viewer sends.

* Shares for some peers

An application sharing with some of its peers, as drover shares a session's terminal with the host that opened it, gives =spyglass-share= a predicate of connections, =:peers=: the lists of shares (=shares=, =list=) are made per connection, and =open= from a connection it refuses answers =closed= with =no such share=, as for a share that does not exist. =:read-only= may be a predicate of connections too: input from the viewers it accepts is refused, and the =in= of =meta= is told per subscription, so that each mirror knows whether it may type. Sharing again with another predicate closes the subscriptions of the viewers it no longer accepts (=unshared=). A share may also have its own =:size-policy=. These options live beside the share's slots, in a table keyed by share, so that shares made by an older spyglass, loaded before, keep working. Nothing of it is on the wire: a viewer of any version opens such shares.

A mirror that closed, its connection gone for good, may be opened anew in its buffer (=spyglass-open= with =:buffer=), emptied first, so that the windows showing it show the new mirror; =:title= names it in its header line.

* Input

The viewer sends text or keys; the owner applies them in the shared buffer through, in order, the share's =:input= function, the buffer's =spyglass-input-function= (set by adapters), or =spyglass-default-input=: in comint buffers, at the input point (below); in other buffers with a process, text and keys go to the process as a terminal sends them (=spyglass-key-bytes=); other editable buffers take text at point. A share made with =:read-only= refuses input, and says so. Input is applied with =inhibit-interaction= bound: a command that would ask the owner's user, as an interrupt asking for confirmation, fails and is reported to the viewer, never keeping the owner's Emacs waiting for someone who is not there.

** Points

Each party has its own point: the owner's buffer has its point and its windows theirs, and a mirror's windows have the viewer's, which moves freely, to read. What a mirror shows of the owner is a cursor, an overlay (=spyglass-cursor=), at the position the owner's =spyglass-point-function= gives: a terminal's cursor for terminals, through their adapters; the input point for a comint buffer; else the point of a window of the owner's showing the buffer, or the buffer's. A mirror's windows follow that cursor while their point is where it was, so that moving away to read stops following; sending input from a mirror brings its window's point back to the cursor, which it follows again, since typing goes there.

The input point of a comint buffer (=spyglass-comint-input-point=) is the buffer's point while it lies in the input, after the process mark, where the owner or a viewer edits it, else the end of the buffer. Text a viewer types goes there and the input point moves past it, as typing there does, and with it the owner's windows whose point was there, so that a window showing the prompt shows the cursor after what was typed, while one where the owner reads elsewhere stays. Keys edit the input there: =DEL=, =<delete>=, =C-d=, the arrows left and right, =<home>= and =<end>= (=C-a=, =C-e=), never past the process mark into output; =RET= submits from the end; =C-c= interrupts; =M-p=, =M-n= and the arrows up and down recall the history. Point was not moved before: text went in at the end with point kept, so that a window's point, a marker staying before text inserted at it, stayed before the text typed, and mirrors showed the cursor behind it.

A front end may submit and interrupt with commands of its own: agent-shell binds =RET= to =agent-shell-submit= (remapping =comint-send-input=, which in its buffers only records the input, as shell-maker sets =comint-input-sender=, committing the line, inserting a newline and sending nothing) and =C-c C-c= to =agent-shell-interrupt=. Viewers' keys are never looked up in the owner's keymaps; the buffer's =spyglass-key-commands= lists the commands an application lets them run, by key as a viewer sends it, which comint buffers run at the input point (=RET= from the end) before their own defaults: drover lists there what a shell it shares binds to =RET=, =M-RET=, =M-p= and =M-n=, and its own interrupt for =C-c=. =spyglass-submit-function= remains, for =RET= alone.

* Structures print in proportion

Emacs prints a value whole wherever nothing bounds it: an error's data, what =format= and =prin1-to-string= are given, a value evaluated, the list of timers. Without =print-circle=, its printer prints a structure again from every path reaching it, cutting only cycles back to what it is printing. Each request pending on a connection, which the connection holds until answered, held a timer whose closure led back to the connection, and so to every other request and its timer: each timer printed every request, and the list of timers the square of their number. Drover found it with recaps of 50 of a host's sessions pending, its connection printing past 4 MB. Shares held their subscriptions, and each subscription its share and connection, so that each printed all the others; mirrors likewise, through their connection. A reply a request's handler keeps for later, in a timer of the application's, held the connection with every request.

Whatever leads back up to what holds it goes through a reference (=spyglass--ref=): an uninterned symbol whose value is the target, which prints as its name, =spyglass-ref=. A subscription holds its share and connection so, a mirror its connection, a process its connection (property =spyglass-connection=), and timers and closures kept for later hold the connection they act on so: heartbeat, reconnection and expiry timers (=spyglass--run-with-timer=), the handshake's watch, the function a transport is given, a channel's sending timer, a request's timer and callback, a reply handed to an application. Each structure prints once, from where it is held: a subscription, mirror, request or timer under 1 kB whatever their number. =spyglass--deref= takes a target stored directly as it is, as a spyglass predating references stored them, so that a running Emacs loading a new spyglass keeps its connections.

Rings of samples, in the statistics of shares and mirrors, were made whole, 4096 numbers each, printing 16 kB or more however few samples they held; they grow with their samples now, up to that size.

=spyglass-print-test.el= shares 40 buffers, mirrors each over two connections, and leaves 40 channel requests pending each way and their 80 replies kept by the application, then prints whole, counting characters and stopping at the bound, so that a failure is quick rather than a runaway: every variable of spyglass, global or local to a buffer, =timer-list= and each timer, and the filters, sentinels and properties of processes, each within 64 kB and 8 kB per share; each subscription, mirror, request and timer within 4 kB. Before references, every one of these failed.

* Security

- The server listens on 127.0.0.1 only; reaching it from elsewhere takes SSH.
- Clients present a 256-bit random token from the registration file (=/dev/urandom= where there is one; else a SHA-256 of Emacs's generator, which the system seeds, and of what varies between instances); the comparison takes constant time.
- Before authentication, frames are limited to 64 KB; after, to 64 MB.
- Nothing received is read or evaluated: JSON, data decoding, sanitizers on the viewer. Keys a viewer sends are applied by the share's input function, never looked up in the owner's keymaps.
- A process filter, sentinel or timer never signals: errors go to =spyglass-error-functions= and callbacks.

* Batch Emacs

Interactive Emacs ignores SIGPIPE; batch Emacs keeps its default action, so writing to a peer that just closed kills a batch Emacs before the write can fail. Tests, benchmarks and any batch use run Emacs with SIGPIPE ignored (=trap '' PIPE= before =exec=; the disposition is inherited).

A batch Emacs waiting in =accept-process-output= runs the timers that are due, but does not wake for a timer armed during the wait, a timer re-arming itself for instance: =wait_reading_process_output= retries for new timers only when it redisplays, which =accept-process-output= does not ask for. Waiting 50 ms at a time made 1 ms timers fire every 54 ms, and spyglass's flushes late. An interactive Emacs waits in its command loop, which redisplays and retries. Tests and benchmarks wait only until the next timer is due (=spyglass-test-step=, =spyglass-bench-step=).

* Emacs on Windows

Emacs on Windows emulates =select= with a thread per socket or pipe, which reads one byte ahead or waits for a connection, and tells the main thread when done (=w32proc.c=). Besides writes to sockets blocking (see Paced streams), three of its ways matter here.

- A listener deleted leaves its thread polling, every 500 ms, before it notices (=_sys_wait_accept=). Meanwhile, a listener given the same descriptor accepts one connection, then none: the old thread cancels its notifications. A server restarted at once did so ten times in ten, one started 0.6 s later never. =spyglass-server-start= waits until 0.6 s after the last =spyglass-server-stop= (=spyglass--listener-linger=); =spyglass-conn-server-restarted-accepts= checks it. The tests start a server each; other code deleting a listener of its own in the same Emacs is beyond spyglass's reach.
- The main thread, writing, and a socket's thread, reading ahead, both switch the socket between blocking and not (=sys_write= and =_sys_read_ahead= in =w32.c=), unguarded. A read ahead made non-blocking that finds nothing fails, and Emacs takes the failure for the end of the stream: "connection broken by remote peer", on a socket nobody closed. Plain Emacs did so twice in six runs of 300 MB written from a polling loop on one loopback connection; the tests writing 16 MB frames to their own Emacs, in about one run in twenty. A stream that breaks so comes back as after any failure: mirrors resume, channel messages under way are lost, and applications resume through =:attach=.
- Processes run through pipes, never ptys: the tests sizing a pty skip there.
- Writes to a pipe do not block: a write the pipe cannot take fails with =ENOSPC=, which =sys_write= reports as =EAGAIN=, and =send_process= waits 20 ms, or a tick of the system's timer, about 16 ms, more. A pipe holds 4 KB unless =w32-pipe-buffer-size= said otherwise when it was made: the SSH transport makes its pipes =spyglass-w32-pipe-size= (4 MB), and channels keep the bytes in flight within it (see Windows of channels).

Measured on Windows 11 with Emacs 31.1 (MSYS2 UCRT64).
